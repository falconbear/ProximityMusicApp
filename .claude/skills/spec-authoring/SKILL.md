# spec-authoring — 仕様書作成ガイド (planner 専用)

このスキルは planner エージェントが `docs/spec.md` を書くときだけ使う。他エージェントは読む必要がない。

## 原則

### 1. WHAT/WHY のみ、HOW は書かない (PIPELINE.md §1)

- **書いてよい**: ユーザーから見える機能、ユーザーフロー、画面の振る舞い、目的、制約事項
- **書いてはいけない**: 技術選定、フレームワーク名、DB スキーマ、API エンドポイント、ライブラリ名、コード例
- 理由: HOW は generator の領域。planner が決めると generator の最適判断を奪う

### 2. 具体的かつ野心的 (ECC gan-planner 準拠)

**保守的な計画は凡庸な結果を生む**。Generator は十分能力があるので、十分な挑戦を与える。

- ユーザーの短いプロンプト (1〜4 行) から、明示されていない機能も含めて完成度の高い製品像を描く
- **機能数の目安: 12〜20 個** (控えめにしない)
- **Sprint 数の目安: 5〜12 個**
- **プロダクト名を必ず付ける** (「このアプリ」ではなく具体名)
- **UI プロジェクトの場合、デザイン方向を具体化**:
  - カラーパレット (「モダン」ではなく `#1a73e8 primary, #f8f9fa background` のように具体値)
  - タイポグラフィ (フォント選択と階層)
  - レイアウト思想 (「密度の高いダッシュボード」vs「余白のある単一ページ」)
  - 視覚的アイデンティティ (AI-slop を回避する独自要素)
  - インスピレーション元となる既存サイト/アプリ

### 2.5 AI-Slop アンチディレクティブ (UI プロジェクト向け)

spec.md に以下を明示して evaluator の減点対象にする:

- **禁止**: 汎用グラデーション (`#667eea → #764ba2`)、ストック Hero、Material UI デフォルト、Unsplash プレースホルダ、汎用カードグリッド
- **要求**: 意見のあるカラーパレット、カスタムレイアウト、意味のあるアニメーション、人格ある empty state、ユーザーを助けるエラー状態
- **エッジケース必須**: empty state / error state / loading state / responsive 挙動を全 Sprint の受け入れ基準に含める

### 3. 実装可能な粒度

- 各 Sprint は generator が 1 回の実装サイクルで完結できるサイズ
- 依存関係がある Sprint は順序を守る (前提となる機能を先に)
- Sprint 01 にはプロジェクト初期セットアップ (init.sh) を含める

## 出力フォーマット

`templates/spec.md` を**コピーして穴埋め**する。見出し階層・フィールド名を勝手に変えない。変えるとパイプライン下流 (progress バリデータ・pr-body 合成) が壊れる。

## Scope / Out of scope / 受け入れ基準

各 Sprint には 3 点セットを必ず書く。これが generator との契約の原料になる。

### Scope
- ユーザーから見える振る舞いレベルで書く
- 例: 「ログインフォームを表示」「検索結果が 10 件ずつページネーションされる」
- NG 例: 「React Router で /login ルートを追加」← 技術詳細

### Out of scope
- このスプリントで**絶対にやらない**ことを明示
- 類似機能との混同を防ぐ
- 例: 「ソーシャルログインは Sprint 03 で扱う」「パスワードリセットは Sprint 05」

### 受け入れ基準 (Success Criteria)
- **Given-When-Then 形式を推奨**
  - 「ユーザーがログインフォームにメールとパスワードを入力し、ログインボタンを押すと、ダッシュボードに遷移する」
  - 「空のメールでログインボタンを押すと、『メールを入力してください』というエラーが表示される」
- **禁止**: 「良い感じに」「適切に」「自然に」「使いやすく」— 測定不能な表現
- **目安**: 1 Sprint あたり 3〜8 個
- evaluator が Playwright で実機テストできる粒度まで具体化する

## ワークフロー

1. **入力を分析** — ユーザーのプロンプトからプロダクトの本質を理解する
2. **市場調査** (必要に応じて) — WebSearch で類似プロダクトを調べ差別化ポイントを特定
3. **機能の洗い出し** — コア機能・補助機能・発展機能をリストアップ
4. **Sprint 分割** — 依存関係を考慮して機能を Sprint に分割
5. **仕様書の出力** — `docs/spec.md` に書き出す
6. **サマリ報告** — 総機能数・総 Sprint 数・最も重要な設計判断・スコープ外事項を 3〜5 行で親に報告

## 起動ガード

- `docs/spec.md` が既に存在する場合は**上書きしない**。親に「再計画してよいか」を確認する
- 再計画が承認されたら既存 spec.md を `docs/spec.archived-YYYY-MM-DD.md` に退避してから書き直す

## 出力後のチェック

以下を自己検証:

- [ ] 全 Sprint に Scope / Out of scope / 受け入れ基準がある
- [ ] 受け入れ基準に曖昧語 (「良い感じに」等) が無い
- [ ] 技術選定やスキーマが書かれていない
- [ ] 各機能を Issue として GitHub に登録し、controller.py init で .ai/work/<id>/ を初期化している
- [ ] Sprint 01 に init.sh / プロジェクト初期セットアップが含まれる
